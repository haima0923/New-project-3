## 1. 任务范围与验收标准

这是局部铺路任务，复查输入 → 确认 → 保存 → 读取结果的受影响链路。
本轮不交付新页面、不接入新 AI、不切换生产保存、不承诺全部上线验收通过。

按产品规则、业务流转、代码与测试三个视角只读评估，再串行实现和复查。
用户已授权继续修复上轮发现的日期问题，并将技术实现委托给 Codex。

最小范围是保存计划内的日期取值，以及用于验证新旧保存语义的样例和门禁。
扩展核查发现审计清单遗漏一个物理写入位置，因此补齐静态清单与对应断言。

人工验收标准：

1. 未填写实际收款日期时留空，不用保存当天、订单交期或预计收款日替代。
2. 明确填写的实际收款日期原样保存，不被当天覆盖。
3. 新报价未给有效期时留空，明确给有效期时保留；不默认追加七天。
4. 定金、部分收款、待收余额、客户与订单关联不因日期修复改变。
5. 多商品缺少价格依据时仍须核对，不能用整单人工标记跳过。

本轮业务实现仅修改 `utils/record-save-plan-builder.js`；
`utils/record-save-shadow.js` 只补审计元数据，不改状态比较或实际写入逻辑。
其余为专项测试、旧测试兼容和文档。未修改 parser、business、storage、页面、
app/config、服务端、发布配置及生产模式。

## 2. 已修复问题

### 业务日期

- 原 Shared `createPayment` 无条件把 `paidAt` 写成保存当天，不仅给空值补日期，
  还覆盖已填写的实际收款日期；现在逐条传递确认结果中的日期。
- 普通 `record_payment` 保留现有 `paymentDate || dueDate` 兼容约定，明确收款日期优先。
- 新订单含定金、已有订单定金、未关联定金、新建待收并收首款仅使用 `paymentDate`，
  防止把交期或预计收款日期记成实际收款日。
- 新报价 `validUntil` 从固定“当天加七天”改为使用确认结果，未提供则留空。
- 报价关联转订单时，沿用现有已核实客户，不额外改动客户的更新时间与最近交易日期，
  与现有 Legacy 行为一致。

记录创建时间等既有系统元数据规则未在本轮重新设计，也不扩展报价编辑等其他行为。

### 测试样例与安全保护

- “多商品无顶层总额”正例原话未写单价，字段却带价格，并试图用整单 manual_fields 确认。
  改为原话明确给出逐商品单价；仍不提供顶层总额，并断言两商品汇总为 1600。
- 原来的无价格原话另存为反例：必须被单价风险挡住，提交不得成功，状态零变化。
- 旧计划失效正例补上报价选择已确认的前置条件；另行断言未确认报价时仍阻止生成可提交计划。
- Preview 和事务样例使用其固定业务时钟，路径比较统一为 `/`，消除当前月份和 Windows 分隔符误报。
- 旧测试统计的 22 个代表场景修正为当前实际执行的 23 个，继续精确检查数量。

### 保存审计清单

记录页已有“取消报价”和“删除记录”两个 `saveState` 位置。旧清单把第一个误标为删除，
且遗漏第二个。两处现有实现均经过统一存储门面；本轮没有改动页面保存行为。

清单现在覆盖 24 个物理写入位置、21 个生命周期、23 种 writerSource。
报价取消和删除分别归类；沿用它们当前共同使用的 `RECORD_SOFT_DELETE` 来源标识，
没有顺手改动生产来源枚举。检查继续要求实际源码扫描结果与清单逐项一致。
