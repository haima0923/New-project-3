# 货小玲多 Agent 协作流程

本文件定义货小玲项目中 Codex 多 Agent 的工作方式。这里的“多 Agent”不是多个真实独立软件机器人，而是 Codex 按角色分工完成分析、实现、复查和测试设计。

## 1. 总原则

1. 多 Agent 主要用于只读分析和复查。
2. 真正改代码时，通常只允许一个实现 Agent 串行修改。
3. 其他 Agent 负责检查，不并行改同一文件。
4. 每个任务必须先判断：局部铺路任务，还是完整交付任务。
5. 每个用户功能必须按用户链路验收。
6. 不懂编程的产品负责人只需要描述页面、输入、期望结果、实际问题和验收标准。

## 2. 角色分工

### 2.1 主控 Agent

职责：

- 理解本轮用户目标。
- 判断任务类型：局部铺路 / 完整交付。
- 选择需要参与的 Agent。
- 汇总多 Agent 结论。
- 控制允许修改范围。
- 决定是否进入实现阶段。
- 输出最终结果和下一步。

主控 Agent 不应该一开始就改代码。

### 2.2 产品规则 Agent

职责：

- 判断需求是否符合货小玲定位。
- 防止功能膨胀成 ERP、CRM、财务软件、进销存。
- 检查是否出现假数据、虚假能力或过度设计。
- 检查用户文案是否像义乌中小工厂老板能理解的话。

### 2.3 用户链路 Agent

职责：

从用户角度检查完整路径：

```text
输入 → 识别 → 确认卡 → 保存 → 记录页 → 详情页 → 问一句 → 测试
```

重点判断：

- 用户从哪个页面开始？
- 用户输入什么？
- 系统应该识别什么？
- 确认卡应该展示什么？
- 保存后去哪里能看到？
- 记录页、详情页、问一句是否需要同步支持？
- 本轮是否遗漏用户可见链路？

### 2.4 代码地图 Agent

职责：

- 只读梳理项目结构。
- 定位页面、工具函数、存储、配置、测试文件。
- 标出高风险文件。
- 判断某个需求可能涉及哪些文件。

代码地图 Agent 默认不改代码。

### 2.5 UI Agent

职责：

- 检查微信小程序页面结构、移动端体验、空状态和长文本。
- 检查确认卡、按钮、文案、页面跳转。
- 保证页面像老板随手使用的工具，不像后台系统。

### 2.6 Parser / AI Agent

职责：

- 检查 `utils/parser.js`、`utils/ai-parser.js`、`utils/parse-safety.js` 等识别链路。
- 判断问题是否属于识别错误、字段提取错误、低置信、待整理兜底问题。
- 区分本地规则和真实大模型能力边界。
- 修改 parser 前必须要求测试样本和回归方案。

### 2.7 业务流转 Agent

职责：

- 检查报价、订单、待收款、收款、订单定金、催款之间的流转。
- 防止重复生成订单、重复生成待收款、错误核销、错误挂定金。
- 判断保存结构和状态变化是否安全。

### 2.8 测试与回归 Agent

职责：

- 根据本轮任务设计最小有效测试。
- 检查是否越权改文件。
- 检查是否遗漏用户链路中的明显页面。
- 输出人工验收路径。
- 明确“已验证”和“未验证”。

### 2.9 配置发布 Agent

职责：

- 检查 `app.js`、`app.json`、`project.config.json`、小程序权限、插件、API 地址、发布风险。
- 配置文件改动必须单独说明原因。

### 2.10 实现 Agent

职责：

- 在方案和文件范围确认后，串行修改代码。
- 不顺手重构。
- 不修改禁止文件。
- 不提交 commit，除非用户明确要求。
- 修改后输出实际改动文件、影响范围和验证方法。

## 3. 局部铺路任务

定义：只搭一个基础能力，不承诺完整用户链路可用。

例子：

- 确认卡支持 `items[]` 商品明细展示。
- 确认卡显示原始内容。
- 记录页把“应收”改成“待收”。

要求：

- 必须写清楚这轮完成什么。
- 必须写清楚这轮没有完成什么。
- 不得把局部铺路包装成完整功能已完成。

## 4. 完整交付任务

定义：用户从输入到查询都能完整使用。

例子：多商品订单完整交付应包括：

1. 用户输入多个商品。
2. parser 拆出多个 `items[]`。
3. 确认卡显示多商品。
4. 用户确认保存。
5. 订单详情页显示多商品。
6. 记录页摘要不丢信息。
7. 问一句可以查到相关订单和商品。
8. 测试覆盖典型样本和边界样本。

要求：

- 必须按完整用户链路设计。
- 可以拆阶段，但每阶段边界必须清楚。
- 涉及 parser、business、storage 时必须更谨慎。

## 5. 标准工作流程

### 第一阶段：多 Agent 只读分析

不改代码。输出：

1. 任务类型：局部铺路 / 完整交付。
2. 用户链路。
3. 涉及页面。
4. 涉及代码区域。
5. 高风险文件。
6. 建议拆分阶段。
7. 第一阶段最小修改范围。
8. 验收标准。

### 第二阶段：用户确认方案

产品负责人确认：

- Codex 是否理解需求。
- 范围是否过大。
- 哪些能力本轮不做。
- 是否允许进入代码修改。

### 第三阶段：单实现 Agent 修改

允许修改代码时，必须明确：

- 允许修改文件。
- 禁止修改文件。
- 本轮目标。
- 本轮不处理内容。
- 不提交 commit。

### 第四阶段：测试与回归 Agent 复查

实现后只读复查：

1. 是否越权改文件。
2. 是否符合用户链路。
3. 是否遗漏明显页面。
4. 是否影响旧功能。
5. 是否需要人工验证。
6. 是否建议提交。

### 第五阶段：人工验收

产品负责人按页面和用户输入测试，不需要看代码。

### 第六阶段：提交 / 推送

只有验收通过后，再 commit 和 push。不要自动合并到主线。

## 6. 可以并行的任务

- 代码地图只读分析。
- 产品规则检查。
- UI 体验评审。
- Parser 风险评估。
- 业务流转风险评估。
- 测试清单设计。
- 配置发布风险只读检查。
- 文档草案审阅。

## 7. 必须串行的任务

- 修改同一个文件。
- 修改 parser。
- 修改 business / storage。
- 修改页面保存逻辑。
- 修改 app.js / app.json / project.config.json。
- 数据结构升级或兼容迁移。
- 真实 AI / 后端联调。

## 8. 经验教训：记一笔确认卡展示基础改造

在 `feature/record-confirm-card-items` 中，第一轮只做了确认卡展示基础改造。后来发现两个漏项：

1. 记录页筛选标签仍显示“应收”。
2. 完整确认卡没有稳定显示原始内容。

原因：第一轮任务按文件范围执行，未按完整用户链路验收。

结论：以后所有用户端功能都要先走用户链路 Agent，不能只按文件修代码。

同时，“椅子、凳子”被合并成一个商品名，是 parser 多商品识别问题，不属于确认卡展示层。不能在确认卡层硬拆。
