# 记一笔确认卡字段标准规格

本文档定义“货小玲”记一笔确认卡的标准字段、类型规则、待整理规则和后续实现顺序。它是后续改造 `pages/input`、`pages/dashboard`、`utils/parser.js`、`utils/business.js` 等文件前的产品与技术约束，不代表本轮已经修改代码。

## 1. 目标与边界

记一笔确认卡的目标不是 100% 自动猜对，而是让老板在保存前看懂、确认、纠正。AI 或本地规则识别出的业务类型只是建议，最终以用户确认结果为准。

确认卡必须做到：

- 明确内容识别准确。
- 不确定内容不要强行分类。
- 模糊内容进入待整理。
- 原始输入 `originalText` 必须保留。
- 用户确认后再保存。
- 不加入假客户、假金额、假订单。
- 不做成复杂 ERP 表单。
- 报价和订单必须支持“一个客户 + 一个业务类型 + 多个商品”的确认结构。

## 2. 用户可见业务类型

确认卡支持以下用户可见类型：

| 用户可见名称 | 内部类型 | 说明 |
| --- | --- | --- |
| 报价 | `quotation` | 记录给客户报了什么价，重点是后续跟进 |
| 订单 | `order` | 记录客户下单，重点是交期 |
| 待收款 / 欠款 | `receivable` | 记录谁还欠钱，什么时候预计收 |
| 收款 | `payment` | 记录客户实际付了多少钱 |
| 订单定金 | `order_deposit` | 记录某个订单收到定金 |
| 催款提醒 | `todo` + `todoType: dunning` | 优先作为提醒，不单独做复杂催款正式记录 |
| 待办提醒 | `todo` | 记录要提醒老板做的事 |
| 待整理 | `pending` | 不确定、缺字段、冲突或多业务混杂时的兜底 |

## 3. 核心产品原则

1. AI 识别出的类型只是建议，最终以用户确认为准。
2. 完整“记一笔”页必须支持手动切换业务类型。
3. 首页快捷确认卡保持轻量，不强制支持复杂类型切换。
4. 原始输入 `originalText` 必须保留。
5. 核心字段缺失、低置信或冲突时，不要强行保存为正式业务记录；建议字段缺失时可以保存为不完整记录，但不能伪造字段。
6. 模糊内容进入待整理。
7. 所有字段展示必须老板看得懂，少用财务专业词。
8. 页面不要堆成表格，不要做成重型 ERP。
9. 不允许出现假客户、假金额、假订单。
10. 催款提醒底层优先作为待办提醒的一种，不单独做复杂催款正式记录。
11. 报价和订单支持同一客户下多条商品明细，不应默认拆成多张确认卡或多笔记录。
12. 所有通过记一笔生成的正式业务记录，无论单商品还是多商品，都必须直接保存 `originalText`；解析日志可以作为补充，但不能替代正式记录里的 `originalText`。

## 4. 标准语义字段

确认卡内部应使用一套标准语义字段，不直接把 `dueDate` 用于所有场景。

### 通用字段

| 字段 | 含义 |
| --- | --- |
| `businessType` | 用户确认后的业务类型 |
| `originalText` | 用户原始输入、语音识别文本或粘贴聊天原文 |
| `confidence` | 识别置信度，仅作风险提示，不直接替用户决策 |
| `remark` | 备注、客户特殊要求、未结构化但有用的信息 |

### 客户字段

| 字段 | 含义 |
| --- | --- |
| `customerName` | 客户称呼 |
| `phone` | 手机号，可选 |
| `customerId` | 已匹配客户 ID，用户无需理解 |

### 商品字段

| 字段 | 含义 |
| --- | --- |
| `productName` | 产品名称 |
| `spec` | 规格 |
| `quantity` | 数量 |
| `unit` | 单位 |

报价和订单应新增标准语义字段 `items[]`，用于承载一客户多产品场景。单商品也可以视为只有一条 `items[0]`。

| `items[]` 子字段 | 含义 |
| --- | --- |
| `productName` | 商品名称 |
| `spec` | 规格 |
| `quantity` | 数量 |
| `unit` | 单位 |
| `unitPrice` | 单价 |
| `totalAmount` | 该商品金额 |
| `itemDeliveryDate` | 单个商品交期，仅在不同商品不同交期时使用 |
| `itemRemark` | 单个商品备注 |

说明：

- 报价和订单不应只依赖单个 `productName`、`quantity`、`unitPrice`。
- `items[]` 是报价和订单的标准商品明细结构。
- 旧的单商品字段可继续作为兼容输入，但后续确认卡应优先转换为 `items[]` 展示。
- `itemDeliveryDate` 主要用于订单中不同商品不同交期的特殊情况；报价中通常为空。
- 如果 item 有 `quantity` 和 `unitPrice`，`item.totalAmount` 可以自动计算。
- 如果多个 item 都有 `totalAmount`，整单 `totalAmount` 默认等于 `items[].totalAmount` 汇总。
- 如果用户明确给了整单总金额，且和商品明细汇总不一致，需要提示用户确认。
- 如果金额冲突严重且用户未确认，应进入待整理。
- MVP 阶段不强制每个商品都有单独金额。

### 金额字段

| 字段 | 含义 |
| --- | --- |
| `unitPrice` | 单价 |
| `totalAmount` | 总价 |
| `receivableAmount` | 待收款金额 / 欠款金额 |
| `paymentAmount` | 本次收款金额 |
| `depositAmount` | 定金金额 |
| `remainingAmount` | 剩余未收金额 |

### 日期字段

| 字段 | 含义 | 用户文案 |
| --- | --- | --- |
| `quoteFollowupDate` | 报价后需要跟进客户的日期 | 跟进日期 |
| `orderDeliveryDate` | 订单需要交付的日期 | 交期 |
| `receivableDueDate` | 预计收款或欠款到期日期 | 预计收款日期 / 到期日 |
| `paymentDate` | 实际收款日期 | 收款日期 |
| `todoRemindDate` | 待办提醒日期 | 提醒日期 |

### 关联字段

| 字段 | 含义 |
| --- | --- |
| `quotationId` | 关联报价 |
| `orderId` | 关联订单 |
| `receivableId` | 关联待收款 / 欠款 |

## 5. 各类型字段规则

### 5.1 报价

- 用户可见名称：报价
- 内部 `businessType`：`quotation`
- 确认卡显示字段：客户称呼、手机号、跟进日期、商品明细列表 `items[]`、备注、原始内容
- 必填字段：客户称呼、至少一条商品明细 `items[0].productName`
- 建议补充字段：数量、单价、总价、跟进日期
- 可选字段：手机号、规格、单位、商品备注、整单备注
- 保存去向：报价记录
- 何时进入待整理：客户无法确认、没有任何商品名、多商品数量 / 单价 / 金额对应关系分不清、同一句话含多个客户或多个业务类型且无法拆分、金额冲突、低置信字段未确认
- 原始文本如何保留：正式报价记录必须直接保存 `originalText`；如进入待整理，保存到待整理记录
- 用户文案建议：使用“跟进日期”，不要把报价日期字段叫“交期”

多商品规则：

- 如果一条报价里有多款产品，应显示为同一张报价确认卡下的多条商品明细。
- 不要默认拆成多张报价。
- 报价中的 `itemDeliveryDate` 通常为空，除非用户明确对某个商品说了特殊交付时间。
- 报价 MVP 阶段只有整单 `quoteFollowupDate`。
- 不支持每个商品单独跟进日期。

### 5.2 订单

- 用户可见名称：订单
- 内部 `businessType`：`order`
- 确认卡显示字段：客户称呼、手机号、订单交期、定金金额、商品明细列表 `items[]`、备注、原始内容
- 必填字段：客户称呼、至少一条商品明细 `items[0].productName`
- 建议补充字段：数量、单价、总金额、交期、定金
- 可选字段：手机号、规格、单位、商品单独交期、商品备注、整单备注
- 保存去向：订单记录；如果有定金金额，定金挂到订单下面
- 何时进入待整理：客户不确定、没有任何商品名、多商品数量 / 单价 / 金额对应关系分不清、同一句话多个客户或多个业务类型无法拆分、定金金额冲突、交期冲突严重
- 原始文本如何保留：正式订单记录必须直接保存 `originalText`；如进入待整理，保存到待整理记录
- 用户文案建议：日期字段叫“交期”，不要叫“到期日”

多商品规则：

- 如果一笔订单里有多款产品，应显示为同一张订单确认卡下的多条商品明细。
- 不要默认拆成多笔订单。
- MVP 默认使用订单总交期 `orderDeliveryDate`。
- 只有当用户明确表达不同商品有不同交期时，才使用 `items[].itemDeliveryDate`。
- 例如“杯子周三交，饭盒周五交”才记录每个商品的 `itemDeliveryDate`。
- 如果用户只说“这批货周五交”，不需要为每个商品强制填写交期。
- MVP 阶段多商品订单只保留整单状态。
- 暂不做每个商品独立生产状态、独立发货状态。
- 只有后续明确升级时，再支持 item 级状态。

### 5.3 待收款 / 欠款

- 用户可见名称：优先使用“待收款”或“欠款”，不建议在用户界面优先展示“应收款”
- 内部 `businessType`：`receivable`
- 确认卡显示字段：客户称呼、手机号、待收金额、预计收款日期 / 到期日、备注
- 必填字段：客户称呼、待收金额
- 建议补充字段：预计收款日期 / 到期日
- 可选字段：手机号、关联订单、备注
- 保存去向：待收款 / 欠款记录
- 何时进入待整理：客户缺失、金额缺失、金额冲突、同名客户无法确认
- 原始文本如何保留：正式待收款记录必须直接保存 `originalText`；如进入待整理，保存到待整理记录
- 用户文案建议：用户看到“待收款 / 欠款”，代码内部仍可使用 `receivable` 作为技术字段名，不建议在用户界面优先展示“应收款”

待收款日期规则：

- 预计收款日期 / 到期日是建议补充字段，不是硬必填。
- 没有日期时，可以保存为“无到期日待收款”。
- 不能伪造日期。
- 不能仅因为缺日期就强行进入待整理。

### 5.4 收款

- 用户可见名称：收款
- 内部 `businessType`：`payment`
- 确认卡显示字段：客户称呼、手机号、本次收款金额、匹配的待收款、收款日期、备注
- 必填字段：客户称呼、本次收款金额
- 可选字段：手机号、匹配的待收款、收款日期、备注
- 保存去向：收款记录；如有关联 `receivableId`，再核销对应待收款
- 何时进入待整理：无法判断客户、无法判断金额、金额冲突严重且用户未确认
- 原始文本如何保留：正式收款记录和未关联收款记录都必须直接保存 `originalText`；不确定时保存到待整理
- 用户文案建议：使用“本次收款”“这笔钱收了多少”，不要直接要求用户理解“核销”

收款规则：

- 如果客户和收款金额明确，即使无法匹配 `receivableId`，也保存为“未关联收款”。
- 未关联收款不能自动核销旧账。
- 只有客户不明确或金额不明确时，才进入待整理。
- 如果匹配到明确 `receivableId`，才可以核销对应待收款。

### 5.5 订单定金

- 用户可见名称：订单定金
- 内部 `businessType`：`order_deposit`
- 确认卡显示字段：客户称呼、产品、定金金额、匹配订单、备注
- 必填字段：客户称呼、定金金额
- 可选字段：产品、匹配订单、备注
- 保存去向：如果能匹配 `orderId`，挂到订单下面；不能作为独立订单保存
- 何时进入待整理：客户不明确、定金金额不明确、金额冲突严重且用户未确认
- 原始文本如何保留：正式定金记录和未关联订单定金记录都必须直接保存 `originalText`；不确定时保存到待整理
- 用户文案建议：使用“这笔定金属于哪一单”，不要把定金当成普通订单

订单定金规则：

- 如果客户和定金金额明确，但无法匹配 `orderId`，可以保存为“未关联订单定金”。
- 未关联订单定金不能当成普通订单。
- 未关联订单定金不能当成普通收款自动核销。
- 只有客户不明确或定金金额不明确时，才进入待整理。

### 5.6 催款提醒

- 用户可见名称：催款提醒
- 内部 `businessType`：`todo`
- 附加字段：`todoType: dunning`
- 确认卡显示字段：客户称呼、提醒事项、提醒日期、可关联的待收款、备注
- 必填字段：提醒事项或客户称呼、提醒日期
- 可选字段：`receivableId`、待收金额、备注
- 保存去向：优先保存为待办提醒，不单独做复杂正式催款记录
- 何时进入待整理：无法判断催谁、无法判断提醒时间、同一客户多笔待收款且无法确认、催款对象与金额冲突
- 原始文本如何保留：正式催款提醒必须直接保存 `originalText`；不确定时保存到待整理
- 用户文案建议：使用“提醒我催一下”“什么时候提醒”，不要让用户理解复杂催款流程

### 5.7 待办提醒

- 用户可见名称：提醒
- 内部 `businessType`：`todo`
- 确认卡显示字段：提醒事项、提醒日期、客户称呼、产品、备注
- 必填字段：提醒事项、提醒日期
- 可选字段：客户称呼、产品、数量、金额、备注
- 保存去向：待办提醒记录
- 何时进入待整理：没有提醒事项、没有提醒日期、事项含义不清、同一句话包含多个提醒但无法拆分
- 原始文本如何保留：正式待办提醒必须直接保存 `originalText`；不确定时保存到待整理
- 用户文案建议：使用“提醒我做什么”“提醒日期”

### 5.8 待整理

- 用户可见名称：待整理
- 内部 `businessType`：`pending`
- 确认卡显示字段：原始内容、系统猜测类型、已识别字段、缺失字段、需要确认的地方
- 必填字段：`originalText`
- 可选字段：`guessedType`、`missingFields`、`rawFields`、`lowConfidenceFields`、`fieldConflicts`
- 保存去向：待整理记录
- 何时进入待整理：类型不确定、核心字段缺失、低置信、冲突、多业务混杂、无法稳定拆分
- 原始文本如何保留：必须完整保存 `originalText`
- 用户文案建议：使用“先放到待整理，晚点补一下”，不要说“解析失败”

## 6. 多商品和多业务边界

确认卡支持：

- 一个客户。
- 一个业务类型。
- 多个商品。

例如：

- “给王总报保温杯 500 个 12 元，饭盒 300 个 8.5 元，周五跟进。”
- “张总下单杯子 500 个、饭盒 300 个，下周五交，先收定金 2000。”

以上应生成一张报价或一张订单确认卡，卡片里包含多条 `items[]` 商品明细。

确认卡暂不强行支持：

- 多个客户。
- 多个业务类型。
- 多条记录混在一句话里。
- 多客户、多商品、多金额互相交叉且无法稳定拆分。

如果一句话里混有多个客户、报价、订单、收款等多个业务类型，且无法稳定拆分，应进入待整理。后续可以再设计“多张确认卡逐条确认”，但不属于当前 MVP 默认能力。

## 7. 商品明细 UI 原则

商品明细不要做成复杂 ERP 表格。确认卡应使用卡片式商品行，适合手机快速扫一眼。

推荐展示方式：

```text
商品1：保温杯
数量：500个
单价：12
金额：6000

商品2：饭盒
数量：300个
单价：8.5
金额：2550
```

UI 原则：

- 多商品仍然属于同一张确认卡。
- 每个商品是一条轻量商品行或小卡片。
- 不使用密集表格、复杂列头、批量编辑器。
- 不强制每个商品填写所有字段。
- 对缺失字段使用“建议补充”，不要让老板感觉必须维护完整商品档案。
- 只有订单中明确不同商品不同交期时，才显示每个商品的单独交期。

## 8. 字段映射规则

现有代码仍可能使用旧字段。后续实现时，应在确认卡层建立标准字段，再在保存层映射到当前存储结构。

| 标准字段 | 当前保存字段 / 去向 |
| --- | --- |
| `items[]` | 报价 / 订单商品明细；旧代码可临时映射到单个 `productName`、`quantity`、`unit`、`unitPrice`、`totalAmount` |
| `items[0].productName` | 兼容旧单商品字段 `productName` |
| `items[0].quantity` | 兼容旧单商品字段 `quantity` |
| `items[0].unit` | 兼容旧单商品字段 `unit` |
| `items[0].unitPrice` | 兼容旧单商品字段 `unitPrice` |
| `items[0].totalAmount` | 兼容旧单商品金额字段 `amount` / 保存字段 `totalAmount` |
| `items[].itemDeliveryDate` | 订单多商品不同交期时的单项交期；报价中通常为空 |
| `quoteFollowupDate` | 报价保存字段 `deliveryDate` |
| `orderDeliveryDate` | 订单保存字段 `requiredDeliveryDate` 和 `expectedShipDate` |
| `receivableDueDate` | 待收款保存字段 `dueDate` |
| `todoRemindDate` | 待办保存字段 `remindDate` |
| `paymentAmount` | 收款记录金额 |
| `depositAmount` | 定金金额，挂到订单付款记录 |
| `totalAmount` | 报价 / 订单总价 |
| `receivableAmount` | 待收款 / 欠款金额 |
| `originalText` | 所有记一笔生成的正式业务记录和待整理记录都必须直接保存；解析日志可以补充记录，但不能替代正式记录里的 `originalText` |

注意：不要继续在确认卡语义层把所有日期都叫 `dueDate`。`dueDate` 可作为历史兼容字段存在，但不应作为新规格中的通用日期语义。

兼容规则：

- 新规格以 `items[]` 为准。
- 如果旧 parser 只输出单商品字段，应在确认卡层转换为 `items[0]`。
- 如果后续 parser 已输出 `items[]`，确认卡不应再只取第一条商品。
- 多商品保存结构如何落库，需要单独确认后再改 `utils/business.js` 和本地存储结构。

## 9. 首页快捷卡规则

1. 首页快捷卡保持轻量。
2. 简单记录可以直接确认保存。
3. 复杂记录建议跳转完整“记一笔”页处理。
4. 首页不强制支持完整类型切换。
5. 首页不能为了省事把复杂内容错误保存。
6. 首页也必须保留 `originalText`。
7. 首页出现低置信、字段冲突、多业务混杂、无法匹配客户 / 订单 / 待收款时，应优先提示去完整页或存到待整理。
8. 首页快捷卡不应展示复杂表格，不应加入 ERP 式多层字段。
9. 首页遇到多商品报价或多商品订单时，可以展示摘要；如果无法完整确认商品明细，应跳转完整页或进入待整理。

## 10. 待整理规则

字段缺失要分成“核心字段缺失”和“建议字段缺失”两类处理：

- 核心字段缺失：不能直接保存为正式业务记录，应进入待整理或要求用户补充。
- 建议字段缺失：可以保存为不完整记录，但不能伪造字段，不能用默认日期、默认金额或假客户补齐。

各类型核心字段如下：

- 报价：客户称呼 + 至少一个商品名。
- 订单：客户称呼 + 至少一个商品名。
- 待收款 / 欠款：客户称呼 + 待收金额。
- 收款：客户称呼 + 收款金额。
- 订单定金：客户称呼 + 定金金额。
- 待办提醒：提醒事项 + 提醒时间。
- 催款提醒：客户或事项 + 提醒时间。
- 待整理：`originalText`。

以下情况必须进入待整理，或至少阻止直接保存为正式记录：

1. 类型不确定。
2. 核心字段缺失。
3. 同一句话包含多个业务且无法拆分。
4. 收款无法判断客户或金额。
5. 订单定金无法判断客户或定金金额。
6. 未关联收款或未关联订单定金的信息不足以形成可追溯记录。
7. 催款无法判断对象或提醒时间。
8. 低置信字段未确认。
9. 字段冲突，例如聊天里前后价格、数量、交期互相覆盖。
10. 多个同名客户无法确认。
11. 多笔订单或多笔待收款无法确认关联对象，且不能按未关联记录安全保存。
12. AI / 本地规则只给出猜测但没有足够依据。
13. 多个商品无法分清数量、单价、金额对应关系。
14. 多商品中字段冲突严重。
15. 同一句话包含多个客户且无法分清每个客户的商品。
16. 同一句话包含报价、订单、收款等多个业务类型且无法拆分。
17. AI 只能识别出一堆商品名，但无法判断业务类型。

待整理记录应保存：

- `originalText`
- `guessedType`
- `rawFields`
- `items`
- `missingFields`
- `lowConfidenceFields`
- `fieldConflicts`
- `source`
- `reason`

## 12. 后续代码实现建议

建议后续按以下顺序实现，不要一轮里同时改 parser、确认卡、保存结构和测试：

1. 先让确认卡支持 `items[]` 展示。
2. 再兼容旧的单商品字段 `productName` / `quantity` / `unitPrice`。
3. 再统一确认卡字段语义。
4. 再统一确认卡展示文案。
5. 再统一保存映射。
6. 再处理 `originalText` 保留。
7. 再处理首页快捷卡降级策略。
8. 再补多商品测试。
9. 最后再优化 parser 的多商品识别准确率。

### 第一轮建议

第一轮只建议处理完整“记一笔”确认卡的字段语义和展示文案：

- 先让完整确认卡能展示 `items[]` 商品明细。
- 把旧单商品字段兼容转换为 `items[0]`。
- 把确认卡内部日期语义拆成 `quoteFollowupDate`、`orderDeliveryDate`、`receivableDueDate`、`todoRemindDate`。
- 用户可见文案使用“待收款 / 欠款”，代码内部可继续使用 `receivable`。
- 保持保存结构暂时不变，只做确认卡到旧字段的映射说明或轻量适配。
- 首页快捷卡先保持轻量，不强行补完整类型切换。

### 测试建议

后续实现后至少补以下场景：

- 报价：跟进日期不被当成订单交期。
- 报价：同一客户多款产品显示在同一张报价确认卡。
- 订单：交期保存到订单交期字段。
- 订单：同一客户多款产品显示在同一张订单确认卡。
- 订单：不同商品不同交期时才使用 `items[].itemDeliveryDate`。
- 待收款：预计收款日期保存为待收款到期日；没有日期时可保存为无到期日待收款。
- 收款：无法匹配待收款时不自动核销。
- 订单定金：不能匹配订单时不变成普通订单。
- 催款提醒：保存为待办提醒，并带 `todoType: dunning`。
- 待整理：低置信、冲突、多业务混杂必须阻止直接正式保存。
- 首页快捷卡：复杂内容不能错误保存。
- 待整理：多商品字段对应关系不清时不能强行正式保存。
- `originalText`：正式记录和待整理记录中必须直接保存，解析日志只能作为补充。

## 13. 必须先确认后才能改的问题

以下问题涉及产品体验、数据结构或历史数据处理，不能由代码 Agent 自行决定：

1. 历史旧记录没有 `originalText` 时是否迁移。
2. 历史旧记录无法补齐 `originalText` 时页面如何展示。
3. 首页快捷卡是否需要“去完整页继续确认”的按钮。
4. 是否允许 parser 输出新字段名，还是先在确认卡层做兼容映射。
5. 是否要为历史本地数据做字段迁移。
6. 多业务混杂输入是否以后支持拆成多张确认卡。
7. 完整记一笔页是否保留所有字段编辑，还是按业务类型进一步收敛。
8. 报价和订单的多商品 `items[]` 如何落库，是新增明细结构，还是先兼容拼接到旧单商品字段。
9. 历史单商品报价 / 订单是否需要迁移成 `items[0]`。
10. 未关联收款在页面上如何展示、如何后续关联待收款。
11. 未关联订单定金在页面上如何展示、如何后续挂到订单下面。
12. 金额冲突提示采用弹窗、确认卡内提示，还是进入待整理后再处理。
13. 多商品中 `itemRemark` 是否需要首轮可编辑，还是先只展示解析结果。
