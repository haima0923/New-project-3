# 货小玲多 Agent 操作指南

本文件给不懂编程的产品负责人和 Codex 使用。目标是让用户只用自然语言描述需求，Codex 按多 Agent 工作流完成分析、实现、复查和验收设计。

## 1. 多 Agent 在本项目里的真实含义

货小玲项目里的“多 Agent”不是多个固定按钮，也不是多个真实独立的软件机器人。

它的真实含义是：Codex 在同一个项目里按不同角色分工工作。

例如：

- 产品规则 Agent 看需求是否符合货小玲定位。
- 用户链路 Agent 看用户从输入到保存再到查看是否完整。
- 代码地图 Agent 找相关文件。
- Parser / AI Agent 看识别逻辑。
- 业务流转 Agent 看订单、待收款、收款、定金是否安全。
- UI Agent 看页面和文案。
- 测试 Agent 设计验收路径。
- 实现 Agent 真正改代码。

## 2. AGENTS.md 和多 Agent 的关系

`AGENTS.md` 是项目最高规则文件。Codex 在项目中工作时应参考它。

但要注意：

- `AGENTS.md` 是项目规则，不等于每次自动启动完整多 Agent 工作流。
- `docs/` 下的详细文档，重要任务时应明确要求 Codex 读取。
- 如果希望 Codex 像编程团队一样分工工作，用户应明确说“启动多 Agent 工作流”。

建议新开 Codex 对话时先让它读取：

```text
AGENTS.md
docs/DOC_INDEX.md
docs/MULTI_AGENT_OPERATING_GUIDE.md
docs/CODEX_DAILY_PLAYBOOK.md
```

如果是记一笔相关任务，还要读取：

```text
docs/RECORD_CONFIRM_CARD_SPEC.md
docs/PARSER_AI_AUDIT.md
docs/BUSINESS_FLOW_AUDIT.md
docs/TEST_AUDIT.md
```

## 3. 用户应该怎么描述需求

用户不需要懂代码，不需要知道文件名。

只需要描述：

1. 在哪个页面。
2. 输入了什么。
3. 希望系统识别成什么。
4. 确认卡应该看到什么。
5. 保存后应该在哪里看到。
6. 当前实际问题是什么。
7. 本轮希望先分析、局部铺路，还是完整交付。

推荐格式：

```text
我要实现的用户结果是：
【一句话说明】

用户路径：
1. 用户在【页面】输入：【原始输入】
2. 系统应该识别为：【业务类型】
3. 确认卡应该显示：【字段和内容】
4. 用户保存后应该在【页面】看到：【结果】
5. 用户后续问一句时应该能查到：【结果】

当前问题：
【实际看到的问题】

请先启动多 Agent 工作流，只读分析，不要直接改代码。
```

## 4. 四种工作模式

### 模式 A：只读分析

适合还不确定问题在哪里。

关键词：

```text
本轮只读，不允许修改任何文件。
请用多 Agent 按用户链路分析。
```

### 模式 B：方案制定

适合准备开工前。

关键词：

```text
请输出完整修改方案，说明这是局部铺路还是完整交付。
不要改代码。
```

### 模式 C：受控自动开发

这是最适合当前项目的日常模式。

关键词：

```text
请按多 Agent 工作流自动执行：先分析，再实现，再复查，再输出人工验收步骤。
允许修改代码，但不要提交 commit，不要 push，不要合并。
```

### 模式 D：自动开发 + 提交

高风险，默认不推荐。只有非常小的文档或样式任务才考虑。

关键词：

```text
允许修改和提交 commit，但不要 push，不要合并。
```

## 5. 标准多 Agent 自动工作流提示词

以下是用户最常用模板。复制后替换【】内容即可。

```text
你现在在“货小玲”项目里工作。

本轮请启动多 Agent 工作流，但不要一开始就写代码。

我的需求是：
【这里写自然语言需求】

用户路径是：
1. 用户在【页面】输入：【输入内容】
2. 系统应该识别为：【业务类型】
3. 确认卡应该显示：【字段/内容】
4. 用户保存后应该在【页面】看到：【结果】
5. 如果系统不确定，应该：【进入待整理/提示补充/不乱保存】

请按以下流程工作：

第一阶段：多 Agent 只读分析
- 产品规则 Agent：判断需求是否符合货小玲定位
- 用户链路 Agent：检查输入、识别、确认卡、保存、记录页、详情页、问一句是否都需要覆盖
- 代码地图 Agent：定位可能涉及的文件
- Parser / AI Agent：判断是否涉及识别逻辑
- 业务流转 Agent：判断是否涉及保存、待收款、订单、收款、定金等业务链路
- UI Agent：判断页面交互和文案
- 测试与回归 Agent：设计验收路径
- 主控 Agent：判断这是“局部铺路任务”还是“完整交付任务”

第二阶段：输出方案
请先输出：
1. 这是局部铺路还是完整交付
2. 用户完整链路是什么
3. 建议拆成几个阶段
4. 第一阶段最小修改范围
5. 允许修改哪些文件
6. 禁止修改哪些文件
7. 验收标准是什么
8. 是否建议现在进入代码修改

如果你判断可以进入代码修改，再继续第三阶段。

第三阶段：单实现 Agent 写代码
- 只能由一个实现 Agent 串行修改代码
- 其他 Agent 只做复查，不并行改同一批文件
- 不允许顺手修无关问题
- 不允许修改禁止文件
- 不允许提交 commit

第四阶段：复查
实现完成后，请让测试与回归 Agent 只读检查：
1. 是否越权改文件
2. 是否符合用户链路
3. 是否遗漏明显页面
4. 是否影响 parser
5. 是否影响 business/storage
6. 是否改变保存结构
7. 人工验证步骤是什么

严格要求：
- 不要自动提交 commit
- 不要自动 push
- 不要合并分支
- 如果必须修改高风险文件，先停止并说明原因
```

## 10. 本项目高风险文件

以下文件或目录改动前必须特别谨慎：

```text
utils/parser.js
utils/ai-parser.js
utils/parse-safety.js
utils/business.js
utils/storage.js
app.js
app.json
project.config.json
project.private.config.json
custom-tab-bar/
server/
scripts/
promptfoo/
```

不是说永远不能改，而是不能顺手改，必须单独说明原因、风险、测试和验收。

## 11. 记一笔链路必须按完整路径看

任何记一笔相关任务，都不能只看一个文件或一个页面。必须先判断是否涉及：

1. 输入页。
2. parser 识别。
3. 安全门控 / 待整理。
4. 确认卡。
5. 保存结构。
6. 记录页。
7. 详情页。
8. 首页工作台。
9. 问一句查询。
10. 测试用例。

如果本轮只做其中一部分，必须明确说明其余部分不完成。

## 12. 本次经验：确认卡展示基础改造

`feature/record-confirm-card-items` 完成的是“完整记一笔确认卡展示基础改造”，不是完整多商品功能。

已完成：

- 确认卡支持商品明细展示基础。
- 旧单商品字段可兼容成 `items[0]`。
- 确认卡显示原始内容。
- 用户可见“应收”文案部分改为“待收 / 待收款 / 欠款”。
- 记录页筛选标签“应收”改成“待收”。

没有完成：

- 多商品自动识别。
- 多商品正式保存结构。
- 多商品订单详情展示。
- 问一句查询多商品。

教训：

- 不能只按文件范围修代码，要按用户链路验收。
- 记录页“应收”漏改，是用户链路没覆盖的例子。
- 确认卡“原始内容”漏显示，是确认卡验收不完整的例子。
- “椅子、凳子”被合并成一个商品名，属于 parser 问题，不能在确认卡层硬拆。

## 13. 下一阶段建议

多商品能力应拆成独立阶段：

1. 确认卡展示基础。已完成。
2. 多商品 parser 识别专项。
3. 多商品保存结构和兼容。
4. 记录页 / 详情页多商品展示。
5. 问一句查询多商品。
6. 回归测试和真实样本评测。

下一阶段如果做多商品 parser，应单独开分支，例如：

```text
feature/parser-multi-items
```
