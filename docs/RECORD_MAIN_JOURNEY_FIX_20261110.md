# 记一笔主流程修复与验收（2026-11-10）

本轮已修复三个会卡住录入的实际问题：普通订单或报价缺客户时无法继续；
补过商品名后仍被旧风险阻止；用户选择待收款后仍被当成未确认。

27 个主流程及边界场景连续两轮全部通过，覆盖输入、逐项补充、确认、保存、记录页与详情重读。
核心 120 题两轮从此前的 10 通过/110 未通过推进为 15 通过/105 未通过，结果稳定。
项目仍未完成上线验收。

## 1. 用户能感受到的变化

| 场景 | 本轮结果 |
| --- | --- |
| 普通订单或报价只缺客户称呼 | 先问是哪位客户，回答后可继续确认；不补造客户 |
| 订单缺商品名 | 回答商品后正确消除这一项风险，不再被无对应身份的旧风险卡住 |
| 缺客户和交期 | 一次只问一项；补齐前不能保存 |
| 用户选了对应待收款 | 记录真实选择的确认依据，满足其他条件后可保存，余额与详情正确 |
| 用户明确选择不关联 | 只记未关联收款，原待收余额保持原值 |
| 信息冲突、超额、旧待收已结清或属于其他客户 | 继续阻止错误保存 |
| 核对超时、服务失败或返回空内容 | 原话保留，不能直接正式保存，可返回修改 |

所有可保存正例均通过真实页面方法调用现有 `saveConfirmedDraft` 与 `saveState`，
再重新加载实际记录页和详情页核对记录、客户、商品、金额及原话。
连续点击只产生一次业务保存和一次存储提交。
这些是 Node PageVM、受控网络响应与隔离 wx 存储证据，不代表微信渲染或真实模型已经验收。

## 2. 任务范围与验收边界

这是局部修复任务，按受影响的完整用户链路验收。用户已同意本轮方案并委托技术实现。
按产品规则、用户链路、代码与回归三个视角串行分析、实现及复查。

生产文件限于：

- `utils/ai-parser.js`：普通客户缺失的追问；商品事实风险的稳定身份绑定。
- `pages/input/input.js`：待收款选择前核对最新客户和待收状态，签发真实操作的字段确认依据。
- `utils/parse-safety.js`：允许待收选择附带的限定元数据变化，并继续绑定金额、客户及风险上下文。

测试与文档包括新增 `scripts/record-user-journey-tests.js`、离线白名单、记录页测试入口，
以及人工确认权限扫描的 Windows 路径规范化。权限扫描仍要求准确命中原有两个批准文件，
没有扩充生产签发权限白名单。

未修改 `utils/parser.js`、`utils/business.js`、`utils/storage.js`、app/config、服务端或发布配置。
现有 Legacy 保存继续使用，Shared 生产提交继续关闭。此前未提交修改全部保留。

人工验收目标：

1. 一条明确订单、报价或待收款可确认保存，并在记录页、详情页看到正确内容。
2. 缺少客户、商品或交期时，回答当前问题后继续；未补齐前不能保存。
3. 收款须明确选择关联对象或不关联；不能自动猜客户或核销对象。
4. 重复点击不重复记账；旧问题、旧选项和已失效关系不能落到新记录。
5. 错误和超时有安全终态，原话不丢。

## 3. 关键实现与风险评估

### 普通客户追问

只在已明确为普通订单/报价、缺少客户且没有既有关系 ID、混合业务、历史/复杂核对信号、
收款或定金字段时生成客户称呼问题。回答继续走现有问题身份、原话指纹、修订和签名校验。
含定金或历史关系的复杂内容仍进入专项核对，不能通过补客户直接取得正式保存资格。

### 商品身份

原先某些单商品事实风险没有 itemKey，页面随后生成另一身份，导致用户回答无法准确消除旧风险。
现在在记录这类风险前给既有商品绑定稳定身份，不新增或拆分商品。
复用已经得到的事实审计，只投影商品身份，不重复扫描原话或增加 parser 调用。

### 待收款确认

选择时重新读取最新状态，验证客户存在、没有合并到其他客户，且待收款仍有效并属于当前客户。
真实选择仅能改变 `receivableId` 及三项对应选择元数据；原风险集保留供签名核对。
选择已有建议或重复点选都不会额外授权其他字段。

不关联选择明确绑定当前客户；真实选择凭据仍绑定完整业务状态。
普通对象中的“已确认”、AI 的建议、复制到另一金额/客户的凭据均不能替代当前真实确认。
其他金额风险、超额核销限制、来源信任及生产 Provider 资格继续检查。

## 5. 剩余问题与下一步

- 105 个未通过结果仍含旧合同、观察期望、样例准备及未归因问题，不能视为 105 个独立功能故障。
- 例如明确单商品订单已可真实页面保存和重读，但 `BASIC-001` 仍因提案的内部来源字段期望不同而失败。
  不能为此改动正确业务行为；后续应按来源证据核对旧合同。
- ASK_USER 与 SAFE_BLOCKED 差异仍分别涉及 37、12 个结果，需逐类确认，而非批量替换 Expected。
- 复查观察到“记一单帆布袋…”等说法可能把指令前缀带入商品名，缺少明确类型时仍需确认类型；
  本轮没有修改原始 parser，应作为后续常用说法识别修复项，不能据本轮正例宣称全部自然说法已可用。
- 本机已检测到微信开发者工具，实际页面、手机录音、真实 AI 成败反馈和线上服务仍未验收。

建议下一轮先处理常用说法识别并核对旧检查来源，代码修改继续串行；
自动检查稳定后进入开发者工具和手机体验验收。没有上传、推送、提交或发布。
