# 业务类型默认与用户修改规则（2026-11-13）

## 用户最新决定

货小玲应根据用户输入、上传内容和相关上下文，默认整理为最可能的业务类型，让老板少点、少填、少学习。类型建议不是要求用户先完成一轮分类；老板可以直接确认，也可以在卡片中修改类型。

不能仅因为本地规则输出unknown，就增加“先选类型”的强制步骤。此前手机验收中“赵姐，礼品盒500套，3块8一套”默认报价，本身不再作为缺陷；此前将其直接判为业务安全缺口的结论撤回。HTTP、语音、数字和其他证据保持原样。

## 默认规则与边界

| 用户表达 | 默认行为 |
| --- | --- |
| 王总水杯500个，每个3.8元，周五交货 | 默认订单，带入原话明确的交期 |
| 给王总报水杯每个3.8元 | 默认报价 |
| 给王总报价每个3.8元，预计周五可以交 | 结合报价阶段，仍优先报价，不因出现“交”字覆盖明确报价 |
| 赵姐，礼品盒500套，3块8一套 | 可根据整体信息建议报价等最合理类型，卡片清楚显示、允许更改，不强制再选一次 |
| 不是报价，客户已经下单了 | 按原话纠正为订单 |
| 先不下单，只问一下价 | 不当成已下单，可按报价理解 |
| 同时包含不同客户、多笔业务或明确互相矛盾的信息 | 只在需要时追问/拆分/待整理，不随便合为一笔 |

理解整段意思，而非机械按关键词分类。“什么时候交货？”可能是问一句；“提醒我问交期”可能是待办；报价阶段的可交时间也不等于客户已下单。

合理默认类型不能成为编造客户、数量、价格、日期或实际收款的理由。确认卡展示后，用户点击确认保存，才保存该类型下的记录；不新增强制确认弹窗。

## 手动修改的用户链路

输入→自动整理并显示默认类型→用户确认或直接改类型→保留客户、原话、商品、数量、单价与适用金额→按新类型显示必要字段→确认后保存。

报价改订单时，报价跟进日期不能偷偷变成订单交期；有明确交期沿用原话，没有交期只补必要信息。订单改报价时，也不能把交货日期当成报价跟进日。更改类型不要求用户重输整段内容，不自动新增一笔记录。

## 本轮执行范围

1. 属于局部产品口径校准及现有能力复核，不是新增分类功能的完整交付。
2. 用户完整链路见上；当前主要核对默认类型与修改后字段保留。
3. 产品规则和用户链路两个角色只读复查，主控串行修正文档。
4. 允许修改本规则、确认卡规格、文档索引、此前验收结论及外部说明；允许运行既有离线验证。
5. 禁止修改parser/business/storage、生产页面与utils、App/配置、服务端、密钥及真实记录；不commit/push/发布。
6. 本轮不修改解析或财务流转，只校准验收标准并验证现有能力。
7. 最小范围是撤回“默认报价本身是缺陷”的结论，补充默认可改原则，不增加强制类型步骤。
8. 人工验收口径：合理默认、类型可改、关键内容保留；不因普通交货/报价句要求用户重复分类。无需用户再录音。
9. 当前已有默认及类型选择入口，本轮不进入生产代码修改；若后续查到具体不符合新口径的行为，先单独复现、界定最小范围。

真实手机类型切换及再次保存尚未验收，不能用离线复核代替真机结果。此前首次失败、首页成功证据及临时记录保存来源仍属原验收待核项。

## 已复核与后续边界

现有Input.changeIntent会调用类型字段投影，报价/订单共享商品和适用金额，根字段的跟进日期与交期在切换时清理。当前已具备自动默认与类型修改入口，本轮未新增强制步骤。

既有离线确认一致性11/11、报价选择及转换25/25通过，统一离线守卫网络尝试0。它们证明现有确认与部分转换合同，不等于已完成手机双向类型切换的完整验收。

只读复查另发现“不要记录赵姐下单礼品盒500套，每套3.8元，11月30日交”仍可能生成可保存订单的否定记录边界，未联网、未点击保存；需单独受控复现，不把它与合理默认混为一个问题，不在本次口径校准中顺手修改parser。
