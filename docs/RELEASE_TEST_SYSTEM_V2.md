## 1. 这套题库测什么

当前题库共 **1,490 道不同输入**，不是重复编号的同一句话。测试程序会先检查每一句是否重复；只要有重复，就直接停止，不生成测试成绩。

| 分类 | 题数 | 主要检查什么 |
| --- | ---: | --- |
| 清楚的单商品订单 | 150 | 简单文字能否由本地规则快速整理 |
| 清楚的报价 | 100 | 报价和订单不能混淆 |
| 清楚的提醒 | 50 | 提醒不能被记成订单或账款 |
| 错别字和同音字 | 160 | 水怀/礼合/钥匙口等语音转字错误 |
| 义乌口语和本地说法 | 140 | 明个儿、礼拜天、五块五、九毛等 |
| 语句顺序颠倒 | 140 | 价格、客户、商品、交期不按顺序说 |
| 微信聊天单条业务 | 100 | 聊天上下文、说话人和原文保留 |
| 改价改量和前后纠正 | 120 | 不对、改成、最后按这个、取消旧值 |
| 多商品订单 | 80 | 两个商品要拆开；一个商品不能误拆成两个 |
| 欠款、收款、定金和催款 | 100 | 不能把收款、定金和欠款混在一起 |
| 缺少关键信息 | 130 | 缺客户、商品、价格、关联订单时不能猜 |
| 混合业务或非业务内容 | 90 | 一句话两笔业务、普通聊天必须待整理 |
| 单商品防误拆回归 | 30 | “20 块钱一个”绝不能多造一个“块钱”商品 |
| AI 失败保护 | 100 | 超时、断网、登录失败、服务错误时不能装作识别成功 |

有限题库不能覆盖世界上每一句话。正确目标是覆盖每一种重要业务、每一种常见说法和每一种危险组合；以后真机发现一条新问题，必须永久加入题库，不能只改代码。

## 2. 每题怎样判定“对”

测试不只看有没有报错，而是逐项检查：

- 业务类型：报价、订单、待收款、收款、定金、提醒或待整理。
- 客户、商品、数量、单价、金额、交期和商品件数。
- 原文没有客户时，是否保持为空，而不是凭空造一个客户。
- 只有一个商品时，是否保持一个商品，而不是把价格词拆成商品。
- 这句话是否应该请求 AI。
- AI 失败时，是否明确显示失败并阻止危险保存。
- 原始输入是否完整保留。

客户、商品、数量、单价、金额、交期、商品件数、错误保存，任一项错了都算失败。严重题错一条就不能被其他题的通过数抵消。

## 3. 本地和 AI 该怎样分工

这不是“本地差就全交 AI”，而是按输入是否清楚分工。

| 最终决定 | 什么时候用 | 后续行为 |
| --- | --- | --- |
| 本地规则即可整理 | 仅限短的手打文字；一件业务；客户、商品、数量、价格清楚；没有改价、历史、账款关联、错别字或矛盾 | 仍展示确认卡，老板确认后才能保存 |
| 请 AI 再核对 | 语音、聊天粘贴、错别字、方言、语序混乱、缺字段、特殊要求 | AI 返回后逐字段核对，不能直接相信 |
| 请 AI 深度整理 | 多轮聊天、改价改量、历史价格、多商品、多笔业务、收款/欠款/定金 | 只要有冲突或证据不足，就要求确认或放待整理 |
| 待整理 | AI 没回来、AI 没有证据、本地与 AI 的关键字段冲突、关键信息缺失、不是业务内容 | 禁止正式保存，只保留原文，等老板补充 |

关键字段是：客户、商品、数量、单价、金额、交期。

本地和 AI 对任意一个关键字段不一致时，系统不能偷偷选一边。必须告诉老板“这里有两个答案，请确认”，或进入待整理。AI 留空客户时，也绝不能把本地猜出来的“老板今”再塞回去。

## 4. 三种证据，必须分开报告

| 证据 | 已经验证什么 | 不能证明什么 |
| --- | --- | --- |
| 本地与路由批量测试 | 本地规则是否识别对；该不该请求 AI；AI 失败状态是否明确 | 不代表真实 AI 理解正确；不代表真机页面可点 |
| 真实 AI 批量测试 | 微信登录后真实 AI 回答、最终合并结果是否正确 | 不代表真实语音转字和屏幕按钮正常 |
| 真机体验版测试 | 真实语音转字、弱网、长确认卡、按钮可点击、保存后回查 | 不代替 1,490 道自动逐字段测试 |

所以报告只能分别说“本地通过多少”“真实 AI 通过多少”“真机通过多少”。任何一项没有验证，都必须写“没有验证”，不能合并成一句“上线测试通过”。

## 5. 历史结果（仅作回归参考）

旧工作树曾生成 1,490 道不同输入的“本地识别 + 路由判断 + AI 失败时保存保护”报告，报告当时记录为 1,490 通过、0 不通过，其中包括 100 道模拟 AI 失败保护题。这些是历史生成报告，不进入 Git 候选快照，也没有在本次冻结中重新运行。

这些历史结果不能证明以下事情：真实 AI 已正确返回、生产 prompt 已被验证、真实页面和保存链路正确，或两个已知 P0 不存在。修复提交 `d652d97` 之前产生的 live AI 结果不得作为发布门禁；本轮 `457f84d` 的离线 fake 动态结果只证明状态和保存保护，不代表真实模型正确率。

历史题库包含以下回归目标；是否仍通过，必须由当前提交上的确定性重跑和后续 P0 回归重新确认：

- “老板今天要订 5 个椅子，20 块钱一个”：客户必须为空，商品只能有椅子一件，数量 5，单价 20。
- “20 块钱一个”以及“五块五、一块二、三毛五”等价格词，不能再被拆成第二个商品。
- 本地错把客户猜错时，AI 留空客户不会再把本地的错误客户强行保留下来。
- AI 没成功返回时，确认卡和保存层都应阻止正式业务保存。

因此当前结论是：**候选快照只保存了当前事实状态，不是发布基线。** 自动生成的逐题报告已经从源代码仓库排除，需要时应由固定提交重新生成。

## 6. 识别速度也必须验收

速度不再只是“感觉快不快”，每次确认卡会记录：本地整理耗时、联网整理等待、总耗时和本次处理方式。

- 清楚的手打文字：优先本地快速整理，不请求 AI。
- 清楚的语音或单条聊天：请求 AI 再核对；界面最多等待 8 秒。
- 改价、多商品、账款、历史关联或多轮聊天：用户主动请求 AI 深度整理；界面最多等待 25 秒。
- 超过等待上限：立即给出基础草稿和明确原因，但不能直接保存为正式业务。

普通请求的服务端快速模型硬上限是 5.2 秒，前端连同本地整理的总等待上限是 8 秒；深度请求的服务端质量模型上限是 20 秒，前端总等待上限是 25 秒。快速模型失败或返回不完整时，当前代码不会自动转质量模型。这些是代码上限，不是真机性能成绩。

## 7. 真实 AI 和真机如何高效验证

本次候选冻结没有读取线上部署元数据，也没有调用真实 AI，因此不能确认线上当前 provider、模型或部署版本。真实验证必须先确认测试环境和微信登录授权，且不得写入生产业务数据。

接下来的真实验证不能用电脑里假接口替代，必须这样做：

1. 在小程序真机或微信开发者工具的已登录环境中，逐题记录：本地草稿、AI 原始回答、最终确认卡、是否保存成功。
2. 两个 P0 的离线 Node 针对性动态回归已经完成；后续真实 AI 验证仍须按批准的成本上限分批执行，先用少量匿名 canary 验证连通性和证据记录，再决定是否扩大题量。每次都要记录模型、provider、生产 prompt 版本、代码提交和测试时间。
3. 真机不需要人工逐条做完 1,490 题，但必须做 60 道代表题：20 道语音、15 道微信聊天、10 道长确认卡、10 道弱网/AI失败、5 道保存后“记录”和“问一句”回查。
4. 真实 AI 或真机发现的任何新错误，都要回填进 1,490 题库，成为永久回归题。

生产 standard/deep prompt 位于 `server/src/ai/model.js`；实验评估 prompt 位于 `scripts/lib/real-ai-comparison-prompts.js`。实验 prompt 的成绩不能代表生产 prompt，更不能代表本地解析、合并、确认卡和保存组成的生产全链路。开始真实 AI 测试前，必须记录每次的“本地答案、AI 原始答案、标准化答案、合并答案、最终保存答案”。

## 8. 本轮文件范围

当前候选工作树包含本地解析、AI 分流和合并保护、保存保护、确认卡、页面与 UI、服务端、题库、测试执行器和公共小程序项目配置。它是冻结快照，不表示这些能力已验收通过。

- `utils/parser.js`、`utils/chinese-number.js`、`utils/text-normalize.js`：修复口语数字、错别字、价格词、客户称呼和商品切分。
- `utils/ai-parser.js`：记录本地/AI/最终答案、分流原因和耗时；防止错误客户覆盖 AI 结果；限制联网等待。
- `utils/business.js`：AI 未成功返回的复杂内容不能正式保存；诊断记录只保留最近 100 条。
- `pages/dashboard/*`、`pages/input/*`：确认卡展示简短的本次整理说明，详情可展开；底部操作按钮避开自定义导航栏。
- `test-fixtures/release-parse-corpus-v2.js`、`scripts/release-parse-corpus-v2.js`：1,490 道不同输入、逐字段判卷、严格路由判断和 AI 失败后的真实保存检查。
- `reports/`、`output/`：只存放可重新生成的本地结果，不进入 Git 源代码候选快照。
