# Codex 多 Agent 日常使用操作手册

这份手册给不懂编程的项目负责人使用。目标是让你可以安全地用 Codex 多 Agent 协作开发“货小玲”，知道什么时候只让它查，什么时候允许它改，怎么防止越权、误改、假数据和重型 ERP 化。

## 1. 货小玲项目当前真实状态总结

货小玲是给义乌中小工厂老板用的轻便 AI 生意助理微信小程序。它不是 ERP，不是复杂管理系统，也不是财务软件。

核心心智是：

- 谁欠钱。
- 哪单要交。
- 哪个报价要跟。
- 老板说一句、打一段、粘贴微信聊天，它帮老板记。

当前真实技术状态：

- 项目是原生微信小程序。
- 数据主要存在本机微信小程序本地存储里，核心是 `wx.setStorageSync`。
- `utils/parser.js` 是本地规则解析器，不是真实大模型。
- 后端、真实 AI、数据库、语音转文字都已有部分预留或联调代码，但不能当成稳定上线能力。
- 当前代码里还有旧名称，例如“生意备忘秘书”，后续要统一为“货小玲”，但必须单独安排修改轮次。

当前最需要谨慎的地方：

- `utils/parser.js`：记一笔怎么识别。
- `utils/ai-parser.js`：本地规则和 AI 接口怎么衔接。
- `utils/business.js`：报价、订单、应收款、收款、催款怎么流转。
- `utils/storage.js`：本地数据结构和兼容。
- `app.js`：API 地址。
- `app.json`：页面、标题、tabBar、权限和插件。
- `pages/input`、`pages/dashboard`、`pages/finance`、`pages/receivables`：核心页面。

当前已知高风险：

- 报价转订单可能重复生成订单。
- 应收款页面收款可能缺少超额和已结清保护。
- 报价交期转订单时可能丢失。
- API 地址和文档描述不一致。
- 语音转文字链路未完全接通。
- 历史测试报告不能直接代表当前代码。

## 2. 每天使用 Codex 前的检查步骤

每天开始前，先让 Codex 做状态确认，不要直接改代码。

建议先问：

```text
你现在在“货小玲”项目里工作。

本轮只做状态确认，不允许修改任何文件。

请确认：
1. 当前项目目录是什么。
2. 当前 Git 分支是什么。
3. 当前 git status 是否干净。
4. 如果工作区不干净，请列出改动文件，但不要处理。

只输出确认结果。
```

你只需要看四件事：

- 目录是不是 `New project 3`。
- 分支是不是你预期的分支。
- `git status` 是否只有你预期的文件。
- 有没有 Codex 不该动的文件。

如果工作区不干净，先不要继续开发，让 Codex 解释哪些文件改了、为什么改。

## 3. 发现 bug 时怎么问 Codex

发现 bug 时，第一轮永远只读分析，不要让 Codex 直接修。

你要提供：

- 问题标题。
- 发生页面。
- 复现步骤。
- 预期结果。
- 实际结果。
- 截图或输入内容。
- 影响模块。
- 优先级。
- 验收标准。

可以直接使用 `docs/BUG_TEMPLATE.md` 里的格式。

第一轮推荐问法：

```text
你现在继续在“货小玲”项目里工作。

本轮目标：只读分析 bug，不允许修改任何文件。

问题：
【这里写问题标题】

发生页面：
【例如：首页 / 记一笔 / 报价 / 订单 / 收款】

复现步骤：
1. ...
2. ...
3. ...

预期结果：
【应该发生什么】

实际结果：
【实际发生什么】

请只读代码，回答：
1. 可能涉及哪些文件。
2. 最可能原因是什么。
3. 是否触碰 parser / business / storage / app.js / app.json。
4. 修复风险高不高。
5. 建议最小修复范围。
6. 建议人工验证步骤。

不要修改文件。
```

## 4. 想新增小功能时怎么问 Codex

新增功能也要先评估，不要直接做。

先问这几个问题：

- 这个功能是否符合“轻便 AI 生意助理”。
- 会不会把货小玲做成重型 ERP。
- 有没有假数据风险。
- 需要改哪些文件。
- 是否会动 parser、business、storage、app.js、app.json。
- 有没有更小的实现方式。
- 怎么验证。

推荐问法：

```text
本轮只做新增小功能前评估，不允许修改文件。

我想新增：
【一句话说明功能】

请评估：
1. 是否符合货小玲定位。
2. 是否有重型 ERP 风险。
3. 可能涉及哪些页面和 utils 文件。
4. 是否需要改 parser / business / storage / app.js / app.json。
5. 最小可行方案是什么。
6. 哪些风险必须先确认。
7. 如果后续允许修改，建议一次只改哪些文件。
8. 人工验收路径是什么。
```

## 5. 想让 Codex 只读分析时怎么问

只读分析要写清楚：

- 只读代码。
- 不修改文件。
- 不运行修复。
- 不重构。
- 输出结论和风险。

推荐格式：

```text
本轮目标：只读分析，不允许修改任何文件。

请作为【某某 Agent】检查：
【写检查范围】

要求：
- 不要修改业务代码。
- 不要修改配置。
- 不要运行修复。
- 不要重构。
- 只输出分析结果、涉及文件、风险和建议。
```

适合只读并行的任务：

- 代码地图盘点。
- 产品规则检查。
- parser / AI 链路分析。
- 业务流转分析。
- 测试能力盘点。
- 配置发布风险盘点。
- UI 风险盘点。

## 6. 想让 Codex 真正改代码时怎么问

允许改代码时，必须明确：

- 只修一个问题。
- 允许改哪些文件。
- 禁止改哪些文件。
- 不要顺手重构。
- 不要加入假数据。
- 修改后必须说明验证步骤。

推荐格式：

```text
本轮目标：只修一个 bug。

允许修改的文件只有：
- 【文件1】
- 【文件2】

禁止修改：
- parser 相关文件，除非上面明确允许
- business 相关文件，除非上面明确允许
- storage 相关文件，除非上面明确允许
- app.js
- app.json
- project.config.json
- 其他无关页面

问题：
【写清楚 bug】

验收标准：
1. ...
2. ...

要求：
- 不要重构。
- 不要加入假数据。
- 不要提交 git commit。
- 修改后输出改了哪些文件、为什么改、怎么验证、是否越权。
```

## 7. 改代码前必须让 Codex 回答哪些问题

在允许 Codex 改代码前，先让它回答：

1. 这次到底要解决什么问题？
2. 最小修改范围是什么？
3. 会改哪些文件？
4. 有没有触碰高风险文件？
5. 是否会影响 parser？
6. 是否会影响 business 流转？
7. 是否会影响 storage 数据结构？
8. 是否会影响 app.js / app.json / 发布配置？
9. 是否会引入假数据？
10. 是否可能让产品变重、变 ERP？
11. 怎么验证？
12. 如果失败，怎么回退或停止？

如果 Codex 说要改 `utils/parser.js`、`utils/business.js`、`utils/storage.js`、`app.js`、`app.json`，必须单独确认后再继续。

## 8. 改代码后必须让 Codex 回答哪些问题

每次改完，必须让 Codex 输出：

1. 本轮修改了哪些文件。
2. 是否修改了业务代码。
3. 是否修改了配置代码。
4. 是否修改了测试脚本。
5. 是否修改了 parser / business / storage。
6. 为什么改这些文件。
7. 修复了什么问题。
8. 有没有加入假数据。
9. 有没有重构无关代码。
10. 运行了哪些测试。
11. 没有运行哪些测试，为什么。
12. 人工验证步骤。
13. 当前 `git status --short` 结果。

不懂代码的人重点只看：

- 改了哪些文件。
- 为什么改。
- 怎么验证。
- 有没有越权。

## 9. 哪些任务可以多 Agent 并行

查问题可以多 Agent，改代码要少 Agent。

适合多 Agent 并行的任务：

- 代码地图只读盘点。
- 产品定位和旧名称风险检查。
- UI 风格和空状态风险检查。
- parser / AI 链路只读分析。
- 业务流转链路只读分析。
- 测试覆盖盘点。
- 配置和发布风险盘点。
- 历史报告整理。
- 人工验收路径整理。
- 提示词模板整理。

这些任务的共同点：

- 主要是读文件。
- 不改代码。
- 不会互相覆盖。
- 结论可以由主控 Agent 汇总。

## 10. 哪些任务必须单 Agent 串行

以下任务必须单 Agent 串行，不要多个 Agent 同时改：

- 修改同一个文件。
- 修改 `utils/parser.js`。
- 修改 `utils/ai-parser.js`。
- 修改 `utils/business.js`。
- 修改 `utils/storage.js`。
- 修改订单、应收款、收款、定金状态规则。
- 修改报价转订单规则。
- 修改客户合并或本地数据结构。
- 修改 `app.js` API 地址。
- 修改 `app.json` 页面、tabBar、权限、插件。
- 修改 `project.config.json` 发布配置。
- 接入真实 AI。
- 接入语音转文字。
- 做数据迁移。

原因很简单：这些地方一改就会影响很多页面和历史数据，多个 Agent 同时动容易互相覆盖。

## 11. 各类 Agent 的职责边界

### 主控 Agent

负责：

- 确认本轮目标。
- 确认允许修改范围。
- 拆分任务。
- 判断并行还是串行。
- 汇总结果。
- 控制最终改动范围。

不能做：

- 在范围不清时直接改代码。
- 默许多个 Agent 同时改同一个文件。

### 代码地图 Agent

负责：

- 只读梳理项目结构。
- 标出页面、工具函数、后端、测试、配置位置。
- 标出高风险文件。

不能做：

- 直接改业务代码。

### 产品规则 Agent

负责：

- 检查是否符合货小玲定位。
- 防止变成 ERP、CRM、复杂财务软件。
- 检查旧名称、假数据、重型 UI、技术化文案。

不能做：

- 擅自改页面文案和样式。

### 解析器 / AI Agent

负责：

- 分析记一笔怎么识别。
- 分析本地规则和 AI 接口边界。
- 检查字段丢失、误分类、待整理风险。

不能做：

- 未经确认就改 parser。
- 假装真实大模型已经稳定接入。

### 业务流转 Agent

负责：

- 检查报价、订单、应收款、收款、催款、定金、客户档案链路。
- 标出状态一致性、重复记录、金额不一致风险。

不能做：

- 未经确认就改 `utils/business.js`。

### 小程序 UI Agent

负责：

- 检查移动端页面体验。
- 检查空状态、文案、按钮、卡片流、导航。
- 防止后台化、表格化、ERP 化。

不能做：

- 用假数据填页面。
- 把页面做成复杂后台。

### 测试与回归 Agent

负责：

- 整理可运行测试。
- 给出最低回归命令。
- 给出人工验收路径。
- 标出测试缺口。

不能做：

- 在不允许时修改测试脚本或报告。

### 配置与发布风险 Agent

负责：

- 检查 `app.js`、`app.json`、`project.config.json`、`.gitignore`、server 部署风险。
- 检查 AppID、API 地址、合法域名、权限、语音、发布前清单。

不能做：

- 未经确认就改配置文件。

## 12. 每次修改后如何用 git status 检查是否越权

每次修改后，让 Codex 运行：

```powershell
git status --short
```

你看输出里的文件。

如果本轮只允许改一个文件，例如：

```text
docs/CODEX_DAILY_PLAYBOOK.md
```

那么 `git status --short` 里只能出现：

```text
?? docs/CODEX_DAILY_PLAYBOOK.md
```

或：

```text
 M docs/CODEX_DAILY_PLAYBOOK.md
```

如果出现这些文件，就要停下来问为什么：

- `app.js`
- `app.json`
- `project.config.json`
- `pages/...`
- `utils/...`
- `server/...`
- `scripts/...`
- `promptfoo/...`
- `custom-tab-bar/...`

检查模板：

```text
请运行 git status --short。

然后告诉我：
1. 当前改动文件有哪些。
2. 是否只包含本轮允许修改的文件。
3. 是否出现业务代码、配置代码或测试脚本改动。
4. 如果越权，请只说明，不要处理。
```

## 13. 每次提交前怎么让 Codex 做复查

提交前不要只问“能提交吗”。要让 Codex 做复查。

推荐问法：

```text
本轮只做提交前复查，不要修改文件，不要提交。

请检查：
1. git status --short。
2. 本轮改动是否符合允许范围。
3. 是否改了业务代码。
4. 是否改了配置代码。
5. 是否改了 parser / business / storage。
6. 是否加入假数据。
7. 是否有重型 ERP 风险。
8. 是否需要运行测试。
9. 是否需要人工验证。
10. 是否可以进入提交准备。

只输出复查结论。
```

提交前必须确认：

- 工作区只有预期文件。
- 没有 `server/.env`。
- 没有 `project.private.config.json`。
- 没有 `node_modules/`。
- 没有 `temp/`。
- 没有无关 `reports/`。
- 没有真实 API Key 或密码。

## 14. 推荐的日常工作流程

推荐每天按这个顺序：

1. 状态确认：目录、分支、`git status`。
2. 只读分析：先查问题，不改代码。
3. 确认范围：允许改哪些文件，禁止改哪些文件。
4. 最小修改：一次只修一个问题。
5. 修改后自查：Codex 说明改了什么、为什么改。
6. 运行必要测试：如果没跑，要说明为什么。
7. 人工验证：按 Codex 给的步骤在小程序里验证。
8. `git status` 检查：确认没有越权。
9. 提交前复查：再让 Codex 做一次只读复查。
10. 再决定是否提交。

最安全的节奏：

- 第一轮：只读分析。
- 第二轮：只修一个点。
- 第三轮：验证和复查。

不要一轮里同时做“查 bug + 改 parser + 改 UI + 改配置 + 提交”。

## 最后记住

- 查问题可以多 Agent，改代码要少 Agent。
- 第一轮永远先只读分析，不要直接改。
- 一次只修一个问题。
- 不要让多个 Agent 同时修改同一个文件。
- 不要把货小玲做成重型 ERP。
- 不要加入假数据。
- 不要随便改 parser、business、storage、app.json、app.js。
- 修改后必须给出人工验证步骤。
- 每次提交前必须确认 `git status`。
- 不懂代码的人只需要看：改了哪些文件、为什么改、怎么验证、有没有越权。
