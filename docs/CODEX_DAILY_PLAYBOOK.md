# Codex 日常使用操作手册

本手册给不懂编程的项目负责人使用。目标是让你可以安全地用 Codex 开发“货小玲”：你只描述用户问题，Codex 负责按多 Agent 工作流分析、实现、复查，但关键节点由你确认。

## 1. 每天开始前先确认状态

不要一上来就改代码。先让 Codex 确认当前目录、分支和工作区状态。

```text
你现在在“货小玲”项目里工作。

本轮只做状态确认，不允许修改任何文件。

请确认：
1. 当前项目目录是什么。
2. 当前 Git 分支是什么。
3. 当前 git status 是否干净。
4. 如果工作区不干净，请列出改动文件，但不要处理。

只输出确认结果。
```

你只看：

- 目录是不是 `New project 3`。
- 分支是不是你预期的分支。
- `git status` 是否干净。
- 有没有不该出现的高风险文件。

## 2. 新开 Codex 对话时先建立上下文

建议第一句话：

```text
你现在在“货小玲”项目里工作。

请先读取：
- AGENTS.md
- docs/DOC_INDEX.md
- docs/MULTI_AGENT_OPERATING_GUIDE.md
- docs/PROJECT_CONTEXT_SNAPSHOT.md

本轮先不要修改文件。请先确认你理解项目定位、多 Agent 工作流、当前重要上下文和高风险文件。
```

如果是记一笔相关任务，再补充读取：

```text
- docs/RECORD_CONFIRM_CARD_SPEC.md
- docs/PARSER_AI_AUDIT.md
- docs/BUSINESS_FLOW_AUDIT.md
- docs/TEST_AUDIT.md
```

## 3. 你如何描述需求

你不需要懂代码。你只需要按用户角度说清楚：

```text
我要解决的问题：
【一句话说明】

用户路径：
1. 用户在【页面】
2. 输入【内容】
3. 点击【操作】
4. 期望看到【结果】
5. 实际看到【问题】

本轮希望：
A. 只读分析
B. 局部铺路
C. 完整交付
```

如果你不确定选 A/B/C，就让 Codex 判断。

## 4. 只读分析怎么问

适合不确定问题在哪，或者准备做新功能前。

```text
你现在在“货小玲”项目里工作。

本轮只读分析，不允许修改任何文件。

我要解决的用户问题是：
【写问题】

用户路径是：
1. 用户在【页面】
2. 输入【内容】
3. 点击【操作】
4. 期望看到【结果】
5. 实际看到【问题】

请启动多 Agent 只读分析：
- 产品规则 Agent
- 用户链路 Agent
- 代码地图 Agent
- UI Agent
- Parser / AI Agent
- 业务流转 Agent
- 测试与回归 Agent
- 主控 Agent

请输出：
1. 这是局部铺路还是完整交付
2. 用户完整链路是什么
3. 涉及哪些页面
4. 涉及哪些代码区域
5. 可能要改哪些文件
6. 哪些文件不能改
7. 建议拆成几个阶段
8. 第一阶段最小修改范围
9. 人工验收标准

不要修改文件。
```

## 5. 让 Codex 像编程团队一样工作怎么说

这是最适合你的常用模板。它允许 Codex 自动分析、实现、复查，但不允许提交代码。

```text
你现在在“货小玲”项目里工作。

本轮请启动多 Agent 工作流。

我的需求是：
【写自然语言需求】

用户路径是：
1. 用户在【页面】输入：【输入内容】
2. 系统应该识别为：【业务类型】
3. 确认卡应该显示：【字段/内容】
4. 用户保存后应该在【页面】看到：【结果】
5. 如果系统不确定，应该：【进入待整理/提示补充/不乱保存】

工作流程：

第一阶段：多 Agent 只读分析。
第二阶段：输出方案，判断局部铺路还是完整交付。
第三阶段：如果方案风险可控，由一个实现 Agent 串行改代码。
第四阶段：实现后由测试与回归 Agent 只读复查。
第五阶段：输出人工验收步骤。

严格要求：
- 不要自动提交 commit。
- 不要自动 push。
- 不要合并分支。
- 不要并行修改同一批文件。
- 如果必须修改高风险文件，先停止并说明原因。
```

## 6. 允许改代码时必须说清楚

```text
本轮允许一个实现 Agent 串行修改代码。

只允许修改：
【列文件】

禁止修改：
【列禁止文件】

本轮目标：
【写清楚】

本轮不处理：
【写清楚】

完成后输出：
1. 实际修改文件
2. 是否修改禁止文件
3. 是否影响 parser
4. 是否影响 business/storage
5. 是否改变保存结构
6. 用户如何验证
7. 风险点

不要提交 commit。
不要顺手修其他问题。
```

## 7. 改完后怎么复查

```text
你现在作为测试与回归 Agent 工作。

本轮只读复查当前未提交 diff，不允许修改文件。

请检查：
1. 是否只改了允许文件
2. 是否误改高风险文件
3. 是否符合本轮用户目标
4. 是否漏掉用户链路中的明显页面
5. 是否影响旧功能
6. 是否需要人工验证
7. 是否建议提交

只输出复查报告。
```

## 8. 你人工验收要怎么做

你不需要看代码。只按用户路径测。

通用验收：

1. 打开对应页面。
2. 输入真实样例。
3. 看确认卡或页面显示。
4. 点保存。
5. 去记录页 / 详情页 / 首页看结果。
6. 重新打开小程序，确认记录还在。
7. 测一个错误或模糊样例，看是否进入待整理。

如果是记一笔，要重点测：

- 报价。
- 订单。
- 待收款 / 欠款。
- 收款。
- 订单定金。
- 待整理。
- 原始内容是否保留。

## 9. 提交前检查

通过人工验收后，再让 Codex 或你自己执行：

```bash
git status
git diff --stat
git diff --check
```

看三个点：

- 是否只有预期文件。
- 改动规模是否合理。
- 是否有明显空白错误。

Windows 上看到 `LF will be replaced by CRLF` 通常只是换行提示，不是代码错误。

## 10. 提交和推送

确认可以提交后：

```bash
git add 【文件列表】
git commit -m "【提交信息】"
git status
git push -u origin 【分支名】
```

不要自动合并到主线。

## 11. 高风险文件

以下文件改动前必须特别谨慎：

```text
utils/parser.js
utils/ai-parser.js
utils/parse-safety.js
utils/business.js
utils/storage.js
app.js
app.json
project.config.json
project.private.config.json
custom-tab-bar/
server/
scripts/
promptfoo/
```

不是永远不能改，而是必须单独评估。

## 12. 局部铺路和完整交付

每次都要问：这轮是局部铺路，还是完整交付？

### 局部铺路

只搭基础，不承诺完整可用。

例子：确认卡先支持 `items[]` 展示。

### 完整交付

用户从头到尾能用。

例子：多商品订单完整交付必须覆盖：

```text
输入 → 识别 → 确认卡 → 保存 → 记录页 → 详情页 → 问一句 → 测试
```

## 14. 最后记住

你只需要管住五句话：

1. 这次是局部铺路，还是完整交付？
2. 用户完整链路是什么？
3. 这次明确不做什么？
4. 改完我怎么验收？
5. 有没有改到禁止文件？
